# What the submit job retries, and when it gives up

ADR-0003 queues each submission and retries it. This decides which answers count as "try again", and when a Generation stops waiting. The rule that decides everything else: a Generation only becomes `failed` locally once Pixelforge has definitely not created it, since a local `failed` is final and a later `succeeded` webhook for it would be ignored, so its real Provider Cost would never be recorded and local numbers would drift from `GET /v1/usage`.

- **Retried, against a budget of 5 attempts** (`MAX_ATTEMPTS`): `rate_limit_exceeded`, `overloaded` and any other 5xx, after `Retry-After` or a 2, 4, 8… s backoff. Either wait is capped at 60 s, below the 120 s after which reconciliation treats a `pending` Generation as stuck; a retry that comes too early is only refused again. Pixelforge documents only three retryable codes, but a 5xx without one (a proxy's `502`/`504`, an unlisted code) is a server failure, not a verdict on the request, so retrying it with the same Idempotency-Key is the safe default.
- **Concurrency limit**: `concurrency_limit_exceeded` means "not yet": Pixelforge runs 3 Generations per account at a time and one can take 90 s or more. For the first 15 minutes after Generate these refusals don't count against the budget ([story 13](https://github.com/ablunier/pixelforge-assessment/issues/1): several quick submissions just wait their turn); after that they do, so nothing waits forever. 15 minutes is about ten Generations' worth of queue at the slowest documented speed.
- **Permanent rejections** (`content_policy_violation`, `validation_failed`, `daily_limit_exceeded`, `idempotency_key_reused`, and any other 4xx): `failed` at once with Pixelforge's code.
- **Exhausted budget**: `failed` with `retries_exhausted`, unless some attempt got no definite answer: a lost response (connection error or timeout), a 5xx other than `overloaded` (documented to create nothing), or a `202` whose body this app can't read or record (reported to the error log). Then Pixelforge may hold the Generation, so it stays `pending` and reconciliation resends it, with the same Idempotency-Key, every couple of minutes. The first resend that gets through returns the existing Generation, if there is one, and the lifecycle applies it. Meanwhile, any webhook for it is still matched by `metadata.generation_id`.
- **Refused API key** (`invalid_api_key`): our misconfiguration, not the Generation's fault. It's reported to the error log, the Generation stays `pending`, and reconciliation resends it, so it goes through once the key is fixed.
- **Hard bound**: a Generation left `pending` for either reason fails after 20 attempts in all (`MAX_ATTEMPTS_AWAITING_PIXELFORGE`, roughly 45 minutes of resends), as `provider_unreachable` or `invalid_api_key`, each with a plain-language reason. The residual risk is a Generation Pixelforge did create while neither 20 requests nor any webhook reached us for that long; the Admin report's usage check against `GET /v1/usage` surfaces it as a day whose Provider Cost doesn't match.

- **One chain of attempts per Generation**: the budget lives on the Generation, so the queue never retries the job itself (`$tries = 1`), and the job is unique per Generation until it starts. A retry still waiting in a busy queue keeps reconciliation from queueing a second one, and attempts are counted with an atomic increment.

## Considered Options

- **Retry only the documented codes, fail on any other 5xx**: would fail a Generation that a gateway timeout may have created at Pixelforge.
- **Fail after the 5-attempt budget whatever the last answer was**: simpler, but loses the Provider Cost of a Generation whose responses were lost ([story 34](https://github.com/ablunier/pixelforge-assessment/issues/1)).
- **Keep resending lost or unauthorised Generations forever**: never loses one, but a user can wait indefinitely and the shared per-minute request limit is spent on them.
- **Throw on a refused key so the job fails**: as loud, but the job's failure says nothing more than the reported exception, and it fills `failed_jobs` every two minutes.
